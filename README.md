# Customer Health & Risk Detection Agent

A small demo agent that combines a customer directory with **Jira** issues
and product usage metrics, and turns it into a color-coded Customer Health
& Risk report — published to **GitHub Pages** and optionally emailed.

Built for 5 fictional customers: Acme Logistics, Northwind Retail, Globex
Manufacturing, BrightPath Healthcare, and Vertex Financial.

## What it does

1. `customers.json` is a plain, hand-edited file holding each customer's
   name, industry, renewal date, and open support cases (subject, status,
   priority).
2. `issues_data.json` holds Jira issues from the `KAN` project, matched to
   customers by looking for the customer's name in the issue summary.
3. `metrics.json` holds product usage metrics (test cases created, dry
   runs, active users — last 7 and 30 days).
4. `health_results.json` holds the health analysis for each account —
   **Green / Yellow / Red**, a short explanation, and a recommended next
   step — weighing open-case severity, open Jira issues, and the usage
   trend together. It's regenerated automatically by `rule_based_scorer.py`.
5. `health_agent.py` merges all four files and renders a single
   color-coded HTML report (`docs/index.html`), then emails it via Gmail
   SMTP if email credentials are configured.

### Why separate data from scoring from rendering

The first version of this called Salesforce, Jira, and the Anthropic API
live on every run. That's a reasonable design for production, but for a
demo it means every test run costs money (metered Claude API calls) and
is fragile (OAuth tokens, API availability). Salesforce also turned out to
be more trouble than it was worth here — the specific org used for this
demo rotated its OAuth refresh token on every use and blocked most of the
simpler auth flows, so it was dropped in favor of a plain static file you
edit directly:

- `customers.json` is a static file — edit it by hand to change a
  customer's cases, industry, or renewal date and see it reflected on the
  next run. No API, no auth, no cost.
- `issues_data.json` is a **snapshot** refreshed on demand via
  `scripts/refresh_jira_data.py` (hits the real Jira API — see
  `jira_client.py`). Jira's API token doesn't expire or rotate on use,
  so once set up it keeps working indefinitely.
- `health_results.json` holds the **health analysis** for the current
  snapshot. It's regenerated by `rule_based_scorer.py` — a small,
  deterministic scorer (fixed weights on open-case priority, open Jira
  issues, and usage trend) with **no LLM call and no API key**, so it can
  run automatically on every scheduled CI run at zero cost. The tradeoff
  is mechanical reasoning ("2 open high-priority cases; usage declining")
  instead of an LLM's more nuanced read — e.g. weighing a near-term
  renewal date alongside the numbers. If you want that nuance back, either
  ask an LLM to rewrite `health_results.json` by hand periodically, or
  swap `rule_based_scorer.py`'s call in the workflow for a live Anthropic
  API call (`claude-haiku-4-5` scoring 5 short accounts costs a fraction
  of a cent per run).
- `health_agent.py` and `report_generator.py` just merge and render —
  no external API calls, no cost, no flakiness, safe to run as often as
  you like (e.g. on a GitHub Actions schedule).

## Architecture

```
rule_based_scorer.py       Regenerates health_results.json (free, no LLM call)
health_agent.py            Merges the 4 JSON files below and renders the report
├── customers.json         Customer directory: name, industry, renewal date, cases (hand-edited)
├── issues_data.json       Jira issues, matched to customers
├── metrics.json           Product usage metrics (see metrics_data.py)
├── health_results.json    Health analysis: score + reasoning + action per account
└── report_generator.py    Renders docs/index.html (color-coded report)

email_sender.py            Emails the HTML report via Gmail SMTP (optional)

scripts/
├── refresh_jira_data.py         Re-fetches issues_data.json from live Jira
└── test_jira.py                 Standalone Jira connectivity check

jira_client.py              Jira Cloud REST API v3 queries + customer matching
metrics_data.py             Generates/loads metrics.json (sample usage data)
```

`metrics.json` is deliberately kept as flat JSON (a plain array of one
object per customer) so it can also be pointed at directly from Grafana
Cloud's [Infinity data source plugin](https://grafana.com/grafana/plugins/yesoreyeram-infinity-datasource/)
for a live dashboard, without any transformation.

## Setup

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# then fill in .env with real credentials — see below
```

### Credentials (`.env`)

Only needed if you want to refresh `issues_data.json` from live Jira, or
want the report emailed. `health_agent.py` itself runs with **no
credentials at all** — it just reads the JSON files.

Copy `.env.example` to `.env` and fill in:

| Variable | Where to get it |
|---|---|
| `JIRA_BASE_URL`, `JIRA_EMAIL`, `JIRA_API_TOKEN` | Your Jira Cloud site URL and an [API token](https://id.atlassian.com/manage-profile/security/api-tokens). Requires a `KAN` project with issues whose summaries mention the customer names. Only needed to run `scripts/refresh_jira_data.py`. |
| `EMAIL_SENDER`, `EMAIL_APP_PASSWORD`, `EMAIL_RECIPIENT` | A Gmail account with an [app password](https://myaccount.google.com/apppasswords) (not your normal password — requires 2-Step Verification enabled). Optional — `health_agent.py` skips emailing if these aren't set. |

`.env` is git-ignored — never commit real credentials.

## Editing customer data

`customers.json` is a plain array — edit it directly to change what the
report shows:

```json
{
  "name": "Acme Logistics",
  "industry": "Shipping",
  "renewal_date": "2026-11-01",
  "cases": [
    {"subject": "Login failures for 3 users", "status": "Escalated", "priority": "High"}
  ]
}
```

After editing, re-run `python rule_based_scorer.py && python health_agent.py`
(or just trigger the GitHub Actions workflow) to see it reflected in the
report.

## Running it

Render the report from the current JSON snapshots (no credentials needed):

```bash
python health_agent.py
```

To refresh Jira first:

```bash
python scripts/refresh_jira_data.py         # needs JIRA_* in .env
python metrics_data.py                      # regenerates metrics.json
python rule_based_scorer.py                 # regenerates health_results.json
python health_agent.py
```

## Publishing the report to GitHub Pages

Every run writes the report to `docs/index.html`. To publish it:

1. Commit and push `docs/index.html`.
2. In the GitHub repo, go to **Settings → Pages**, set **Source** to
   `Deploy from a branch`, branch `main`, folder `/docs`, then save.
3. GitHub will publish the report at
   `https://<your-username>.github.io/<repo-name>/`.

Re-running `health_agent.py` and pushing again updates the published page.

### Automated scheduled runs (GitHub Actions)

[.github/workflows/health-report.yml](.github/workflows/health-report.yml)
runs the full pipeline on a schedule (daily by default — change the cron
expression for hourly) and commits the refreshed report automatically:
refresh Jira (if secrets are set) → regenerate `health_results.json` via
`rule_based_scorer.py` → render → email (if secrets are set) → commit +
push. It costs nothing to run — no Anthropic API call anywhere in the
path — and the Jira refresh step is skipped (falling back to whatever
`issues_data.json` is already committed) unless you've added the matching
secrets under **Settings → Secrets and variables → Actions** (same
variable names as `.env.example`). It can also be triggered manually from
the **Actions** tab (`workflow_dispatch`).

`customers.json` is never touched by the workflow — it's a static,
hand-edited file, so edits to it just need a commit + push (or a manual
workflow trigger afterward) to show up in the published report.
